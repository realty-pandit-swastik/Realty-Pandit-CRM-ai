# Deal Pipeline — Stage 1: NEW (new WhatsApp lead)

> Stage-by-stage "as-is" record of how the AI and the human team member work a deal, what resources/connections each uses, how they coordinate, and where they disconnect. This is the **NEW** stage — a brand-new lead's first WhatsApp message. Built from a full code trace 2026-06-21 (3 parallel investigations, file:line-verified against `.env.production`).
>
> Codebase root: `agents/backend/src/` (frontend `agents/frontend/src/`).

---

## TL;DR (the reality of NEW today)

- A new WhatsApp number → **Contact (type UNKNOWN)** + **Deal in NEW** are auto-created. The contact is **auto-assigned to "Sunny" (the super_boss)** for any `whatsapp`/`voice` source — so **every inbound WhatsApp lead funnels to Sunny**, not a round-robin team member.
- The AI's **first reply is a live free-form WhatsApp** ("Namaste — tell me your budget / location / type"), generated by **Google Gemini**. It delivers because the inbound message opened a 24-hour session.
- The promised **AI outbound qualification CALL does NOT happen** — Omnidim is **stubbed and disabled** (no `OMNIDIM_API_KEY`). It degrades to **one WhatsApp template + a manager alert, then the call cadence halts.**
- The human is alerted via **`fireNewLeadAlerts`** (WhatsApp text + push + in-app bell to Sunny + the assigned agent) and gets a **"📞 Call new lead" task due in 30 min**. That *task* itself is **silent** (no notify()), and the alert funnels to Sunny.
- AI and human can **collide** — both can contact the customer in the same minute, and the bot can **auto-qualify on a bare "hi"** and fire a property card while the human is mid-call.

## A. What happens, in time order

### AI path (Panditji)
1. **Meta → webhook.** Inbound hits `POST /webhooks/whatsapp` (`routes/webhooks.ts:99`). Returns **200 immediately** (Meta's 5s deadline), processes async. ⚠️ **No HMAC/app-secret check on the message path** — the `x-hub-signature-256` is only forwarded for *call* events (`webhooks.ts:115-123`).
2. **Dedup + queue.** `isMessageProcessed(msg.id)` via Redis `msg_dedup:<id>` (`webhooks.ts:131`) → enqueue BullMQ `whatsapp-inbound`, **serial worker concurrency 1** (`queues/workers/whatsapp_inbound.ts:39`). Redis-down fallback runs `processInboundMessage` synchronously (`webhooks.ts:194`).
3. **Open session + identify.** `SessionTracker.markInbound(from)` opens the 24h window (`webhook_processor.ts:78`). `identifyContact()` checks Agent/PartnerAgent/Owner — external buyer matches none → `null` (`contact_identifier.ts:31`).
4. **Create Contact.** `prisma.contact.create` with `contact_type:'UNKNOWN'`, `source:'whatsapp'`, `lead_status:'cold'` (`webhook_processor.ts:120-130`).
5. **`contact.create` `$extends` hook fires** (`db.ts:32-53`):
   - (a) **Auto-assign to Sunny** — `shouldAutoAssignToSunny('whatsapp')` → `assigned_agent_id` = active super_boss (`new_lead_alerts.ts:25-30,73`).
   - (b) **`fireNewLeadAlerts`** (`new_lead_alerts.ts:95`): for BUYER/TENANT/UNKNOWN → **LIVE WhatsApp text** "📋 New Lead in CRM" to Sunny + assigned agent (`:139-155`) + `notify('new_lead_arrived')` = **push + in-app** (`:159-173`).
6. **Create Deal (fire-and-forget, NOT awaited).** `ensureDealForLead({source:'whatsapp'})` (`webhook_processor.ts:138-145` → `ensure_deal.ts:58`): idempotent per (contact, type); lands **status = NEW**, `ai_paused:false` (`:91-97,156`). Keeps Sunny as coordinator/executive. Side effects:
   - **Schedules qualification-call cadence** `scheduleQualificationCall(deal.id, 0)` (`:163-166`).
   - **Creates "📞 Call new lead" task** — direct `prisma.task.create`, `task_type:REMINDER`, `priority:HIGH`, `due = now + 30min`, assignee = Sunny (`:179-198`).
   - **Google sync** `pushReminderToGoogle()` fire-and-forget (`:201-203`).
7. **Lead scoring.** `initScore` then `+10 engagement` per inbound (`lead_score.ts:11,31`); stays `cold` (<60).
8. **First AI reply** (the customer-facing touch). Through guards (card-reply, template-button, auth, calendar, frustration — all skipped for a greeting) to the **central message router** (`message_router.ts:70`): `classifyFull` via **Gemini** → `SalesAgent.handleBuyer` INTAKE (`sales_agent.ts:58`). Decision (`:135`): has location or budget → match (`MatchingAgent` → property card); else → **ASK for budget/location/type** via Gemini, sent as **free-form `sendText`** (`webhook_processor.ts:759`). *(If the opener has a trigger word like "flat chahiye" → `buyerWorkflowAdapter` structured intake instead.)*
9. **Qualification CALL = STUB/OFF.** `isOmnidimConfigured()` = `Boolean(OMNIDIM_API_KEY)` — **absent in prod** (`lead_qualification_caller.ts:236`). Attempt #1 sends template `rp_buyer_lead_received` to the customer + `rp_callback_manager_alert` to the coordinator, logs a `stub:true` interaction, and **halts the cadence** (`:146-183`). Even with a key, `triggerOmnidimCall` is a log-only stub (`:248-252`). **No AI voice call occurs.**
10. **Interaction logging.** Inbound `message` (`:813-822`) + outbound `message` reply (`:782-791`). Safety net: if nothing replied → "🙏 a team member will assist you shortly" + HIGH CALLBACK task (`:852-927`).

### Human path (assigned member — for WhatsApp leads, Sunny)
1. **Gets alerted** by `fireNewLeadAlerts` (step 5b): WhatsApp text + Web Push + in-app bell. *(The "Call new lead" task in step 6 does **not** itself notify — only Google sync.)*
2. **Sees the deal** in the **NEW column** of the Deal Pipeline Kanban (`DealPipeline.tsx:17`); NEW cards show **"🤖 AI calling… {time}"** (`:317-318`). Opens `DealWorkspace.tsx`.
3. **Acts** (all write endpoints require `act_on_deals`):

## C. Coordination signals at NEW
- **Shared status** — one `Transaction.status=NEW`, governed by `transaction_state_machine.ts`.
- **Shared timeline** — Interaction rows + the merged `/timeline` feed; both AI and human writes are visible.
- **`ai_paused`** — default `false` on a new deal; only a hard human "Pause AI" or a closing-signal sets it.
- **`last_team_action_at`** — set by human actions; the AI *caller* backs off 30 min if set, but the AI *inbound auto-reply/auto-qualify* does **not** check it.
- **The 30-min "Call new lead" task** — the human's SLA clock.

## D. The disconnections (what we will fix)

1. **AI voice qualification is OFF (stub).** `OMNIDIM_API_KEY` absent → no call; 1 template then cadence halts (`lead_qualification_caller.ts:146-252`). The "AI qualifies by calling" KRA is unmet; real qualification only happens if the lead replies on WhatsApp.
2. **Every WhatsApp lead funnels to Sunny.** Auto-assign-to-Sunny (`new_lead_alerts.ts:25-30`) means inbound WhatsApp leads are not round-robined to team members; both the alert and the task land on Sunny until someone reassigns. Single bottleneck.
3. **The "Call new lead" task is silent.** `ensure_deal.ts:179-199` skips `notify()` (unlike `createWorkflowTask`/`createLeadActionTask`); only opt-in Google sync. The loudest alert path is the quietest — the human-facing signal relies entirely on `fireNewLeadAlerts` (which targets Sunny).
4. **Double-touch collision.** No mutual guard: the AI fires its template/reply immediately while the human is told to call within 30 min; if the lead replies mid-call the bot auto-qualifies and fires a property card over the human's conversation (`webhook_processor.ts:478-492`).
5. **Stage-exit ambiguity.** Three independent paths move NEW→QUALIFIED — inbound bot on *any* reply (even "hi", `webhook_processor.ts:478`), SalesAgent on location-or-budget (`sales_agent.ts:242`), human (log-call/status). None reconcile; bot can flip stage + send a (possibly empty/wrong) card while the human still sees NEW. Premature/thin qualification.
6. **Notification reliability.** Push needs a stored subscription (may never exist); WhatsApp-to-agent is free-form (fails outside the agent's 24h window); email is unmanaged localhost Postfix. Reliable channels reduce to **in-app bell (requires opening app) + push (if subscribed)**.
7. **Duplicate-deal race (Redis-down).** `ensureDealForLead` dedup is an unlocked read-then-write; no unique constraint on `Transaction.demand_contact_id`. Safe only via the serial worker — the sync fallback (`webhooks.ts:194`) bypasses it, so a Redis outage can fork a lead into two deals.
8. **Swallowed deliverability failures.** Template sends (qualification intro, property card) swallow errors (`lead_qualification_caller.ts:152`, `property_sharing.ts:341`); a Meta template-approval lapse = the customer's first AI touch silently never arrives.
9. **No webhook signature verification** on the inbound message path (`webhooks.ts`).

### Suggested fix priority (highest leverage first)
1. Wire `notify()` into the new-lead reminder + decide the assignment policy (Sunny-funnel vs round-robin) — gaps 2, 3.
2. Guard the bot's auto-qualify on `last_team_action_at` / pending human task — gaps 4, 5.
3. Make Omnidim live, or formally redefine NEW-stage qualification as WhatsApp-first — gap 1.
4. Harden deliverability (template-failure surfacing) + dedup lock + webhook HMAC — gaps 7, 8, 9.

## E. Target design — NEW-stage qualification (decisions 2026-06-21, still in discuss)

**Principle: AI drafts → AI auto-qualifies only if complete *and* confirmed, otherwise hands the human a structured task → the form is the gate, Google Task closes the loop.**

### The qualification parameters (what "qualified" means — the checklist)
A lead is QUALIFIED only when these are captured + verified (today it qualifies on a bare "hi" — to be fixed):
- **genuine?** (not spam / duplicate / wrong-number)
- **intent** — buy / rent
- **category** — residential / commercial *(today: never captured for buyers)*
- **type** — flat / plot / villa / shop / office
- **BHK / size**
- **budget** — real, user-stated range *(today: `budget_min` fabricated as max×0.7)*
- **location** — free-text + geocoded *(today: hardcoded whitelist drops unknown towns)*
- **timeline / urgency** *(today: AI never captures)*

### The flow
1. **AI works autonomously (deal stays NEW, "🤖 draft — X/8 captured").** Engages on WhatsApp/voice, fills the draft profile, runs a pre-screen for genuineness. Does NOT auto-qualify on thin data.
2. **Auto-qualify path (DECIDED: "AI may auto-qualify if complete + confirmed").** When the AI has captured ALL required fields, it **reads the requirement back to the lead for confirmation** ("So: 2BHK flat, Sector 150, ₹80L–₹1Cr, to buy — sahi hai?"). On an explicit "yes" → AI flips NEW→QUALIFIED itself with verified data. No human step needed for clean leads.
3. **Human-task path (incomplete / unconfirmed / silent / low-confidence).** AI creates a **"Qualify lead" task** for the owning agent carrying: the AI draft + checklist of what's missing + a deep link to the qualify form. Sent on **in-app + push + WhatsApp + Google Task** (fixes the silent-task gap #3).
4. **Human closes the loop = the real gate.** Agent opens the task (Google Tasks or app), calls, verifies/corrects the draft, confirms genuine, submits → that submission flips NEW→QUALIFIED (reuses the Log-Call 5-field checklist) AND marks the task done.
5. **Google Tasks (DECIDED: "Google Task + app form, two-way").** Today it's one-way push (CRM→Google). Build the **two-way sync**: a poller/watch reads agents' Google Tasks; ticking the task done closes the CRM task. Because a Google checkbox can't carry data, the **Google Task note holds a deep link to the mobile qualify form** — tapping it qualifies the deal AND checks off the task. (Caveat: some agents must re-grant the Tasks scope — see [[reference_google_tasks_scope_gap]].)
6. **SLA + escalation.** Timer (e.g. 30–60 min) → escalate agent → manager → super_boss.
7. **Collision control.** When a human claims the task, AI pauses proactive outbound to that lead; resumes if SLA lapses. AI also won't fire the task mid-active-conversation. (Fixes double-touch #4.)

### Magicbricks attribution (DECIDED)
- Match `sub_user` on **phone (timesgroup) OR email (personal_email / google_email)** → route to the originating agent. (Today only the timesgroup-phone form matches; agent-Gmail listers — Ashwani, Pooja, Bhuvneswar, Bharat — wrongly round-robin.)
- **Partner-lister** sub_users (e.g. `thenanakestates@gmail.com`, not an internal agent) → **round-robin to the team** (employee pool).
- **No-sub_user** leads → round-robin (and push Magicbricks to always populate the lister field). Open check: quantify how many of the 411 carry no sub_user.
