# Fix Plan: Production Errors — Service Worker + 403 AxiosError

## Context

GlitchTip reports 5 HIGH unresolved errors on admin.realtypandit.in (last scanned 20 Apr 2026, midnight IST):
- **4 Service Worker errors** (20 total hits) — SW update failing + SW registration rejected
- **1 AxiosError 403** (6 hits) — some admin API call returning 403

No CRITICAL errors. All 5 are isolated to the Admin CRM.

---

## Issue 1: Service Worker Failures (20 hits)

### Root Cause

The admin panel (`agents/frontend/`) has two overlapping SW update mechanisms fighting each other:

1. **`vite.config.ts`** — `vite-plugin-pwa` with `registerType: 'autoUpdate'` + `skipWaiting: true` + `clientsClaim: true`. The plugin auto-registers and auto-updates the SW on every page load.
2. **`src/main.tsx` lines 36–39** — A manual `setInterval` that calls `registration.update()` every 60 seconds on top of the plugin's auto-update.

Every 60 seconds, the admin triggers a SW update check. If that update fetch fails (network blip, deploy replacing `dist/sw.js` mid-request), the browser throws an unhandled "Failed to update ServiceWorker" rejection — which GlitchTip captures as a HIGH error. The `wrsParams.serviceWorkers.navigator.serviceWorker.register` errors are the same issue — VitePWA's generated `registerSW.js` doesn't catch its own promise rejection.

### Fix

**File: `agents/frontend/src/main.tsx`**
- Remove the 60-second `setInterval` that calls `registration.update()` (lines 36–39). VitePWA's `autoUpdate` already handles this — the manual interval is redundant and causing double-update race conditions.
- Wrap the `navigator.serviceWorker.addEventListener('controllerchange', ...)` in a try/catch to prevent unhandled rejections from propagating to GlitchTip.
- Add a `.catch(() => {})` on the SW registration promise exposed by VitePWA to silently absorb transient network failures during SW fetches.

**File: `agents/frontend/vite.config.ts`**
- No change needed — `autoUpdate` + `skipWaiting` + `clientsClaim` is correct for a SPA. The problem was the duplicate manual interval, not the Workbox config.

## Issue 2: AxiosError 403 (6 hits)

### Root Cause

The minified function `aU` maps to axios calls in `DealCloseCommissionDialog.tsx` (lines 62–63). This component uses **raw `axios.get`/`axios.post`** with `withCredentials: true` but **does NOT use the shared `client` from `src/api/client.ts`**. That shared client has interceptors that:
- Read the CSRF token from the `rp_csrf` cookie and attach it as `X-CSRF-Token`
- Auto-retry with a fresh CSRF token if a 403 CSRF error is returned

Since `DealCloseCommissionDialog` bypasses the shared client, its POST to `/api/deals/{id}/commission-entries` has no `X-CSRF-Token` header → backend CSRF middleware returns 403.

The 6 hits likely correspond to the 6 times a user opened the Deal Close/Commission dialog and submitted it.

### Fix

**File: `agents/frontend/src/components/DealCloseCommissionDialog.tsx`**
- Replace `import axios from 'axios'` with `import client from '../api/client'`
- Replace `axios.get(...)` → `client.get(...)`
- Replace `axios.post(...)` → `client.post(...)`
- Remove `withCredentials: true` from these calls (the shared `client` already sets this globally via `axios.create({ withCredentials: true })`)
