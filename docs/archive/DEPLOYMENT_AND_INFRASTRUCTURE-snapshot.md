## 2. Domain Routing (Nginx)

Nginx acts as a reverse proxy in front of all three applications. Configuration is generated by `deploy/03-configure-nginx.sh`.

| Domain | Internal Port | Application | Nginx Config File |
|--------|--------------|-------------|-------------------|
| `realtypandit.in` / `www.realtypandit.in` | 7575 (early config) / 3000 (current) | Next.js Website | `/etc/nginx/sites-available/realtypandit.in` |
| `api.realtypandit.in` | 7071 | Express.js Backend | `/etc/nginx/sites-available/api.realtypandit.in` |
| `admin.realtypandit.in` | 5173 | Vite Admin Panel | `/etc/nginx/sites-available/admin.realtypandit.in` |

### SSL Certificates

All domains use **Let's Encrypt** certificates managed by Certbot with the Nginx plugin:

```bash
certbot --nginx \
  -d api.realtypandit.in \
  -d realtypandit.in \
  -d www.realtypandit.in \
  -d admin.realtypandit.in
```

Auto-renewal is handled by the Certbot systemd timer (`certbot renew` runs automatically).

### Nginx Features

**Website (`realtypandit.in`)**
- WebSocket upgrade support (`Upgrade` / `Connection` headers)
- Static asset caching: `/_next/static` with `max-age=31536000, immutable`
- Image caching: `.jpg`, `.png`, `.gif`, `.ico`, `.svg`, `.webp` with 7-day cache
- Security headers: `X-Frame-Options`, `X-XSS-Protection`, `X-Content-Type-Options`, `Referrer-Policy`
- Proxy timeouts: 60 seconds (connect, send, read)

**API (`api.realtypandit.in`)**
- Rate limiting: 30 requests/second with burst of 50 (zone: `api_limit`)
- Extended proxy timeouts: 90 seconds (for long-running AI/chat requests)
- CORS: `Access-Control-Allow-Origin` set to `https://realtypandit.in`
- Allowed methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
- Security: `X-Frame-Options: DENY`

**Admin (`admin.realtypandit.in`)**
- Optional IP whitelisting (commented out by default)
- HSTS header: `max-age=31536000; includeSubDomains`
- `X-Frame-Options: DENY`

## 3. PM2 Process Management

PM2 manages all three Node.js processes. State is persisted with `pm2 save` and restored on reboot via `pm2 startup`.

| Process Name | Port | Mode | Instances | Notes |
|-------------|------|------|-----------|-------|
| `realty-backend` | 7071 | cluster | Multiple (Instance 0 = primary) | Instance 0 runs BullMQ workers + scheduled jobs; other instances handle API traffic only |
| `realty-website` | 3000 | fork | 1 | Next.js production server (`npm start`) |
| `realty-admin` | 5173 | fork | 1 | Vite preview server (`npm run preview --port 5173`) |

### PM2 Cluster Mode (Backend)

The backend uses PM2's cluster mode. The `NODE_APP_INSTANCE` environment variable differentiates instances:

- **Instance 0 (primary)**: Runs BullMQ workers (WhatsApp inbound processor, scheduled jobs worker) in addition to serving API requests.
- **Instance 1+ (workers)**: API-only -- skip worker startup to avoid duplicate job processing.

This logic is in `agents/backend/src/server.ts`:

```typescript
const isPrimaryInstance = !process.env.NODE_APP_INSTANCE
    || process.env.NODE_APP_INSTANCE === '0';

if (isPrimaryInstance) {
    startWhatsAppInboundWorker();
    await startScheduledWorker();
}
```

### Common PM2 Commands

```bash
pm2 list                         # Show all processes
pm2 logs realty-backend           # Tail backend logs
pm2 restart realty-backend --update-env  # Restart with fresh env
pm2 save                          # Persist process list
pm2 startup                       # Generate boot startup script
pm2 monit                         # Real-time monitoring dashboard
```

| **Port** | 6379 |
| **Supervised** | systemd (production) |

### Production Configuration

Redis is installed natively via `apt install redis-server` and configured for systemd supervision:

```bash

```

### Usage in the Application

Redis serves multiple purposes in the backend:

| Use Case | Description |
|----------|-------------|
| **BullMQ Job Queues** | Backend for WhatsApp inbound message processing and all scheduled jobs (pending actions, daily reports, subscription expiry, QA health, AI Boss cycle, follow-ups, call processor, interaction triggers, security scans) |
| **Message Deduplication** | 2-minute TTL keys to prevent duplicate WhatsApp webhook processing |
| **Rate Limit Counters** | Token bucket / sliding window counters for API rate limiting |
| **Session Store** | Temporary session data storage |
| **Cache** | General-purpose caching layer |

### Fallback Behavior

If Redis/BullMQ is unavailable at startup, the backend falls back to legacy schedulers using `node-cron` and `setInterval`:

```typescript
// server.ts fallback
catch (err) {
    logger.error('[Server] BullMQ worker startup failed, falling back to legacy schedulers:', err);
    startLegacySchedulers();
}
```

Legacy schedulers include: `initScheduler()`, `FollowupScheduler`, `callProcessor`, `qaJobs`, `aiBossJobs`, `SecurityAgent`, and `InteractionEngine`.

## 6. Deployment Flow (deploy-now.sh)

`deploy-now.sh` is the **primary deployment script**, executed from the local development machine. It deploys all three applications to the production server over SSH.

### Prerequisites

- SSH key at `~/.ssh/realty_pandit_key` (copied to `/tmp/rp_key` at runtime)
- SSH access to `root@72.62.231.224`

### Step-by-Step Flow

```
[Local Machine]                          [Server: 72.62.231.224]
      |                                          |
      |  Step 1: SSH connectivity check (5s timeout)
      |----------------------------------------->|
      |                                          |
      |  Step 2: Package source code             |
      |  tar.gz with exclusions:                 |
      |    - node_modules                        |
      |    - .next, dist, .git                   |
      |  Includes:                               |
      |    - agents/backend/{src,prisma,pkg}     |
      |    - agents/website/{src,public,pkg,cfg} |
      |    - agents/frontend/{src,public,pkg,cfg}|
      |                                          |
      |  Step 3: SCP upload + extract            |
      |----------------------------------------->|  Extract to /tmp/rp-deploy-extract
      |                                          |  Sync files to /var/www/realty-pandit/
      |                                          |
      |  Step 4: Backend update                  |
      |----------------------------------------->|  cd /var/www/realty-pandit/backend
      |                                          |  npm install --silent
      |                                          |  npx prisma migrate deploy
      |                                          |  npx prisma generate
      |                                          |  npx ts-node prisma/seed_flat_types.ts
      |                                          |  pm2 restart realty-backend --update-env
      |                                          |  curl localhost:7071/health (verify)
      |                                          |
      |  Step 5: Website rebuild                 |
      |----------------------------------------->|  cd /var/www/realty-pandit/website
      |                                          |  npm install --silent
      |                                          |  npm run build (Next.js)
      |                                          |  pm2 delete + pm2 start realty-website
      |                                          |
      |  Step 6: Admin rebuild                   |
      |----------------------------------------->|  cd /var/www/realty-pandit/frontend
      |                                          |  npm install --silent
      |                                          |  npm run build (Vite)
      |                                          |  pm2 restart realty-admin --update-env
      |                                          |
      |  Final: Verification                     |
      |----------------------------------------->|  pm2 save
      |                                          |  systemctl reload nginx
      |                                          |  Health checks on all 3 domains
      |                                          |
      |  Output: Live URLs                       |
      |  https://www.realtypandit.in             |
      |  https://api.realtypandit.in/health      |
      |  https://admin.realtypandit.in           |
```

### File Sync Details

The sync step (Step 3) performs a **selective copy**, not a full overwrite:

- **Backend**: Merges `src/*`, `prisma/*`, `package.json`, `tsconfig.json`
- **Website**: Replaces `src/` entirely, merges `public/*`, copies config files (`next.config.*`, `tailwind.config.*`, `postcss.config.*`)
- **Admin**: Replaces `src/` entirely, copies `index.html`, config files (`vite.config.*`, `tsconfig*.json`)

### Usage

```bash
# From the project root directory
bash deploy-now.sh
```

## 8. Pipeline Tools

All pipeline scripts live in the `pipeline/` directory and are designed to be run from the project root.

**Location**: `pipeline/watch-and-deploy.sh`

Watches the `agents/` directory for file changes and automatically triggers `deploy-now.sh`.

| Feature | Value |
|---------|-------|
| **Linux/WSL mode** | Uses `inotifywait` (inotify-tools) for event-driven detection |

| **Exclusions** | `node_modules`, `.next`, `dist`, `.git`, `.env`, `.log` |
| **Log file** | `pipeline/deploy.log` |

```bash

# Press Ctrl+C to stop
```

**Location**: `pipeline/backup.sh`

Creates timestamped backups of the PostgreSQL database and server source code, stored locally.

| Feature | Value |
|---------|-------|
| **Database backup** | `pg_dump` streamed over SSH to local `pipeline/backups/db_YYYYMMDD_HHMMSS.sql` |
| **Code backup** | `tar.gz` of `backend/src`, `backend/prisma`, `website/src`, `website/public`, `frontend/src` + `package.json` files |
| **Rotation** | Keeps last 7 backups of each type; older files are automatically deleted |
| **Log file** | `pipeline/backup.log` |

# Schedule via cron (example: daily at 2 AM)
# 0 2 * * * cd /path/to/reality-pandit && bash pipeline/backup.sh

### health-check.sh -- Service Monitoring

**Location**: `pipeline/health-check.sh`

Runs a comprehensive suite of checks against all production services.

| Check Category | Tests |
|----------------|-------|
| **Website** | HTTPS returns 200/301; homepage loads HTML |
| **API Backend** | `/health` endpoint responds with `status`; database shows `connected`; `/public/properties` endpoint works |
| **Admin Panel** | HTTPS returns 200/301 |
| **AI Chatbot** | `/public/ai-chat` POST responds with a valid reply; checks for Gemini quota errors |
| **SSL Certificates** | Checks expiry dates for all 3 domains; warns at <30 days; alerts at <7 days |

```bash
# Run health checks
bash pipeline/health-check.sh

# Exit code: 0 = all pass, >0 = number of failed checks
```

**Log file**: `pipeline/health.log`

## 9. Docker Support

### docker-compose.yml (Development / Testing)

Docker Compose is used for **local development and CI testing only**. Production uses native PostgreSQL and Redis installs.

```yaml
version: '3.8'

services:
  postgres:
    image: postgres:15-alpine
    container_name: reality_pandit_db
    ports:
      - "5433:5432"            # Note: mapped to 5433 to avoid conflicts
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: RealtyPandit2026SecureDB!
      POSTGRES_DB: reality_pandit
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: pg_isready -U admin -d reality_pandit
      interval: 10s / timeout: 5s / retries: 5

  redis:
    image: redis:7-alpine
    container_name: reality_pandit_redis
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    healthcheck:
      test: redis-cli ping
      interval: 10s / timeout: 3s / retries: 5
```

### Why Not Docker in Production?

The production server runs **native PostgreSQL 16** and **native Redis 7** installed via `apt` (see `deploy/01-setup-server.sh`). This provides:

- Direct systemd integration and supervision
- Lower overhead (no container layer)
- Simpler backup and restore workflows (direct `pg_dump`)
- Native OS-level tuning

Docker images for the backend and website are built in CI (`docker build`) for verification and potential future containerized deployments, but are not currently used in production.

## 11. Graceful Shutdown

The backend implements a full graceful shutdown sequence, critical for PM2 restarts and deployments to avoid dropped requests and leaked connections.

### Signal Handlers

Both `SIGTERM` (sent by PM2 on `pm2 restart`) and `SIGINT` (Ctrl+C) trigger the same shutdown flow.

### Shutdown Sequence

```
Signal received (SIGTERM / SIGINT)
  |
  |  1. Set isShuttingDown = true (prevent re-entry)
  |
  |  2. server.close()
  |     Stop accepting new HTTP connections
  |     Existing in-flight requests continue processing
  |
  |  3. Stop BullMQ workers
  |     - stopWhatsAppInboundWorker()
  |     - stopScheduledWorker()
  |     Workers finish their current job, then close
  |
  |  4. Grace period: 5 seconds
  |     Allow in-flight HTTP requests to complete
  |
  |  5. prisma.$disconnect()
  |     Release all database connections back to the pool
  |
  |  6. process.exit(0)
```

### Idempotency Guard

A boolean `isShuttingDown` flag prevents multiple signals from triggering concurrent shutdown sequences:

```typescript
let isShuttingDown = false;

async function gracefulShutdown(signal: string) {
    if (isShuttingDown) return;
    isShuttingDown = true;
    // ... shutdown logic
}
```

### Unhandled Error Handling

In addition to graceful shutdown, the server catches:

- **Uncaught exceptions**: Logged, alert sent via `alertCritical()`, then `process.exit(1)` (PM2 auto-restarts)
- **Unhandled promise rejections**: Logged and alerted, but process continues running

## 12. Health Check Endpoint

**Endpoint**: `GET /health`

Returns a JSON object with the overall system health status.

### Response Schema

```json
{
    "status": "ok",
    "database": "connected",
    "redis": "connected",
    "circuits": {
        "gemini": "closed",
        "whatsapp": "closed"
    },
    "memory": {
        "rss": "128 MB",
        "heapUsed": "64 MB",
        "heapTotal": "96 MB"
    },
    "queues": {
        "whatsappInbound": {
            "waiting": 0,
            "active": 0,
            "failed": 0
        },
        "scheduled": {
            "waiting": 0,
            "active": 0,
            "delayed": 5
        }
    }
}
```

### Field Descriptions

| Field | Description |
|-------|-------------|
| `status` | Overall health: `"ok"` or `"degraded"` |
| `database` | PostgreSQL connection state: `"connected"` or `"disconnected"` |
| `redis` | Redis connection state: `"connected"` or `"disconnected"` |
| `circuits.gemini` | Circuit breaker state for Gemini AI API: `"closed"` (healthy), `"open"` (failing), `"half-open"` (recovering) |
| `circuits.whatsapp` | Circuit breaker state for WhatsApp API |
| `memory.rss` | Resident set size (total OS memory used) |
| `memory.heapUsed` | V8 heap memory in active use |
| `memory.heapTotal` | V8 total allocated heap |
| `queues` | BullMQ queue statistics (waiting, active, failed, delayed job counts) |

### Usage in Deployment

The health endpoint is checked automatically during deployment:

```bash
# In deploy-now.sh (Step 4)
curl -sf http://localhost:7071/health

# In health-check.sh
curl -s https://api.realtypandit.in/health --max-time 10
```

## 13. Supplementary Deployment Scripts

In addition to `deploy-now.sh` (the primary deployment tool), several other scripts exist for specific scenarios.

### deploy.sh -- Full Server Bootstrap

**Purpose**: One-time initial deployment on a fresh server. Installs all system dependencies, starts Docker containers, builds all applications, and configures PM2.

**Run on**: The server itself (`sudo ./deploy.sh`)

**Steps**: System update -> Node.js 20 -> Docker -> `docker-compose up -d` -> Backend (npm install, prisma, pm2) -> Website (build, pm2) -> Admin (build, pm2) -> Firewall (ufw)

### deploy-to-server.sh -- Auto-Deployment from Scratch

**Purpose**: Complete hands-off setup of a fresh Ubuntu server. Includes all system package installation, database startup, application builds, PM2 startup configuration, and firewall rules.

**Run on**: The server itself or piped via curl.

**Steps**: 12-step process covering system update, Node.js, PM2, Docker, Nginx, Certbot, project directory setup, database services, backend, website, admin, and final configuration.

### push-update.sh -- Rsync + Remote Rebuild

**Purpose**: Upload changed files via `rsync` from local machine, then execute `update-server.sh` on the server.

**Run on**: Local machine.

**Flow**: `rsync` (excludes node_modules, .next, dist, .git, .env) -> SSH to run `update-server.sh`

### update-server.sh -- Server-Side Update

**Purpose**: Run on the server after files have been synced. Creates a backup, updates all three applications (npm install, build, restart), verifies database services, saves PM2 state, and runs health checks.

**Run on**: The server itself.

**Steps**: Backup -> Backend update (npm install, prisma migrate, pm2 restart) -> Website update (npm install, build, pm2 restart) -> Admin update (npm install, build, pm2 restart) -> Database service check -> PM2 save -> Health checks

## 14. Security Hardening

### Firewall (UFW)

```
22/tcp   ALLOW   # SSH
80/tcp   ALLOW   # HTTP (redirects to HTTPS)
443/tcp  ALLOW   # HTTPS
```

All other ports are denied by default.

### Fail2Ban

Installed and enabled via `deploy/01-setup-server.sh`. Protects against brute-force SSH attacks by banning IPs after repeated failed login attempts.

### Nginx Security Headers

| Header | Website | API | Admin |
|--------|---------|-----|-------|
| `X-Frame-Options` | SAMEORIGIN | DENY | DENY |
| `X-XSS-Protection` | 1; mode=block | 1; mode=block | 1; mode=block |
| `X-Content-Type-Options` | nosniff | nosniff | nosniff |
| `Referrer-Policy` | strict-origin-when-cross-origin | -- | -- |
| `Strict-Transport-Security` | -- | -- | max-age=31536000; includeSubDomains |

### API Rate Limiting

Nginx enforces a rate limit of **30 requests/second** per client IP on `api.realtypandit.in`, with a burst allowance of 50 requests (no delay).

### Automatic Security Updates

`unattended-upgrades` is installed for automatic OS-level security patches.

## 15. Troubleshooting

### Common Issues

**Backend won't start**
```bash
# Check for missing env vars
pm2 logs realty-backend --lines 20
# Look for: "FATAL: Missing required environment variables"

# Verify database connectivity
psql -U realty_user -d reality_pandit -c "SELECT 1"

# Verify Redis connectivity
redis-cli ping
```

**Website build fails**
```bash
cd /var/www/realty-pandit/website
npm run build 2>&1 | tail -50
# Check for TypeScript errors or missing dependencies
```

**Health check returns "degraded"**
```bash
curl -s https://api.realtypandit.in/health | python3 -m json.tool
# Check which field is not "connected" or "closed"
```

**PM2 processes keep restarting**
```bash
pm2 logs --lines 50        # Check error logs
pm2 describe realty-backend # Check restart count and uptime
```

**SSL certificate expired**
```bash
certbot renew --dry-run     # Test renewal
certbot renew               # Force renewal
systemctl reload nginx
```
