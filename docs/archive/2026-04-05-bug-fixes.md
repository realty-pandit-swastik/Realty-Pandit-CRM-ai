## 2026-04-18 — Backend crash cascade (5 bugs)

### Bug 1 — Backend 87-94 restarts (root cause of cascade)
**File:** `backend/src/workflows/workflow_engine.ts` (lines ~42, ~704, ~1039)
**Problem:** `prisma.agent.findFirst/findUnique` used `phone_number` field — Agent model uses `phone`. Prisma threw ValidationError on every inventory submit involving agent phone lookup → backend crashed → PM2 restarted → CSRF tokens wiped → 403 errors in admin → ServiceWorker failures.
**Fix:** Changed to `phone: { in: phoneVariants(...) }` at all 3 locations. Also changed `findUnique` → `findFirst` (phone is not @unique).

### Bug 2 — Rate limiter IPv6 warning flooding logs
**File:** `backend/src/middleware/rate_limit.ts`
**Problem:** `loginLimiter` used custom `keyGenerator: (req) => req.ip ?? 'unknown'` — express-rate-limit v7+ requires `ipKeyGenerator` helper for IPv6. Logged ERR_ERL_KEY_GEN_IPV6 on every startup.
**Fix:** Removed custom keyGenerator entirely (default handles IPv6 correctly).

### Bug 3 — Team members saw ZERO leads
**File:** `backend/src/middleware/contact_visibility.ts`
**Problem:** Apr 17 middleman migration changed employee visibility filter to `{ created_by: agentId }`. But 909/911 contacts had `created_by = NULL` (all pre-Apr-17 leads + inbound WhatsApp). Employees with 200+ assigned leads saw nothing.
**Fix:** Employee filter now `OR [{ assigned_agent_id: agentId }, { created_by: agentId }]`. Manager filter updated similarly to include `assigned_agent` relations.

### Bug 4 — New leads missing created_by
**File:** `backend/src/routes/leads.ts` (POST handler ~line 450)
**Problem:** Prisma create omitted `created_by`/`owning_manager_id` with comment "pending client cache refresh" + used raw SQL workaround. Prisma generated client already had the fields.
**Fix:** Added fields directly to Prisma create. Removed raw SQL workaround.

### Bug 5 — Inventory image review broken
**File:** `backend/src/routes/workflow.ts` line 398
**Problem:** Used `image_urls` — Inventory model stores images as `media_urls String[]`. Prisma crashed silently.
**Fix:** Changed `image_urls` → `media_urls`.

### Key insight
All 4 fields-bugs were the same pattern: **wrong field name on a Prisma model**. Developers used field names from other models by analogy. Lesson: never copy field names without checking `schema.prisma`.

## 2026-04-20 — GlitchTip HIGH errors (5 hits, 3 issues)

### Bug 1 — ServiceWorker "Failed to update" (15 hits)
**File:** `agents/frontend/src/main.tsx`
**Problem:** Two overlapping SW update mechanisms fighting — `vite-plugin-pwa` with `autoUpdate` already handles updates, AND a manual `setInterval` (60s) calling `registration.update()` on top. Every 60s the admin triggered a SW update check; when fetch failed (network blip or deploy replacing `dist/sw.js` mid-request), the browser threw unhandled rejection → GlitchTip captured HIGH.
**Fix:** Removed the 60s `setInterval` block. VitePWA's autoUpdate handles this on its own.

### Bug 2 — ServiceWorker "register rejected" (5 hits)
**File:** `agents/frontend/src/main.tsx`
**Problem:** VitePWA's generated `registerSW.js` calls `navigator.serviceWorker.register()` without catching its own promise rejection. Transient network failures during SW registration flowed into the global `unhandledrejection` handler.
**Fix:** Added SW-specific filter in the `unhandledrejection` handler — checks if `reason` includes `'ServiceWorker'`, `'serviceWorker'`, or `'wrsParams'` and suppresses those from GlitchTip.

### Bug 3 — AxiosError 403 in DealCloseCommissionDialog (6 hits)
**File:** `agents/frontend/src/components/DealCloseCommissionDialog.tsx`
**Problem:** Component used raw `import axios from 'axios'` instead of the shared `client` from `src/api/client.ts`. The shared client has CSRF interceptors; raw axios bypasses them → 403 on every commission save.
**Fix:** Replaced raw axios with shared client. **Rule:** any component doing POST/PUT/PATCH/DELETE MUST use `src/api/client.ts`, never raw axios. See [`feedback_axios_shared_client.md`](memory).

## 2026-04-23 — Catalog + AdminAgent + template fix (5 bugs)

### Bug 1 — Nightly catalog reconcile crashing
**File:** `agents/backend/src/queues/workers/scheduled_worker.ts` line 720
**Error:** `Cannot find module '../services/catalog_sync'`
**Cause:** Worker is at `src/queues/workers/`, service is at `src/services/`. Relative `'../services/...'` resolves wrong.
**Fix:** `'../../services/catalog_sync'`.
**Impact:** Nightly 3:30 AM IST reconcile silently failing — no WhatsApp product data updated nightly.

### Bug 2 — 235 catalog products showing placeholder image
**File:** `agents/backend/src/services/catalog_sync.ts` — `toAbsoluteUrl()`
**Cause:** A previous patch changed base URL from `api.realtypandit.in` to `www.realtypandit.in` AND added a block replacing any `/uploads/pending/` path with placeholder. Facebook crawler confirms `/pending/` URLs return HTTP 200 — they're accessible.
**Fix:** Reverted to `API_BASE = 'https://api.realtypandit.in'`, removed `/pending/` block. **Never add a `/pending/` → placeholder block.** Real image count jumped from 23 → 114 after reconcile.

### Bug 3 — 174 catalog products with "NA" in names
**File:** `agents/backend/src/services/catalog_sync.ts` — `mapInventoryToProduct()`
**Cause:** `bhk = bedrooms ? ... : 'NA'` — "NA" was the fallback when `specs.bedrooms` is null, then included in name template.
**Fix:** Use `filter(Boolean)` to drop empty strings; `bhkLabel = bedrooms ? '<n> BHK' : ''`.

### Bug 4 — Transaction Followup Template 404
**File:** `agents/backend/src/services/interaction_engine.ts` line 364
**Cause:** Code used `'rp_tx_followup_new'` but approved Meta template is `rp_tx_followup_new_v2`.
**Fix:** Updated name. Transaction followups had been silently failing.

### Bug 5 — AdminAgent "Cannot Display Live Listings" on property searches
**File:** `agents/backend/src/agents/admin_agent.ts`
**Cause:** All WhatsApp TEXT messages from team members route to AdminAgent (basic LLM, no tool access). Panditji tools are voice-only via Pipecat.
**Fix:** Added `isPropertySearchMessage()` keyword detector + `searchPropertiesForAdmin()` Prisma query bypassing the LLM for property-search intent. Keywords cover bhk/flat/villa/plot/etc. × search/show/find/list. Cities: vaishali, delhi, noida, gurgaon, greater noida, faridabad, ghaziabad, indirapuram, dwarka, rohini, janakpuri.

## 2026-04-28 — Matching engine + property sharing + login CSRF (5 issues)

### Bug 1 — Inverted budget crash
**File:** `matching_engine.ts` `buildMatchCriteriaFromLead`
**Cause:** Passed budget_min/max as-is even when min > max.
**Fix:** `Math.min`/`Math.max` to auto-swap.

### Bug 2 — broadenLocation left symbols + hyphenated sectors
- "&" in "Sector 4 & 5 Vaisali" survived → broke text search
- "Sector -4 vaishali" didn't match sector regex (hyphen before number) → "Sector" left orphan
**Fix:** `replace(/[^a-zA-Z0-9\s]/g, '')` to strip symbols; `-?` in sector regex; second pass to strip orphan "sector/phase/block/pocket/extension" words.

These two bugs prevented 2 of 7 QUALIFIED deals from ever getting property cards.

**File:** `property_sharing.ts`
**Cause:** If `demand_intent` null → defaulted to 'buy'. Deal `1c68099e` had 14K–20K budget (monthly rent) but matched against sell inventory.
**Fix:** If intent null AND `demand_budget_max < 200000`, infer 'rent'.

### Data fix
Deal `de83a070` had `demand_location = "Sector 4 & 5 Vaisali"` ("Vaisali" typo for "Vaishali"). Fixed directly in DB.

### Login CSRF misleading error
**File:** `frontend/src/api/client.ts`
**Cause:** Axios interceptor was catching 401 from `/auth/login` (wrong password) and trying to refresh session token. Refresh hit `/auth/refresh` with no valid CSRF → 403 CSRF. The CSRF error propagated to the login form, showing "CSRF validation failed" instead of "wrong password".
**Fix:** Added `/auth/login` to the 401 interceptor skip list (alongside `/auth/me` and `/auth/refresh`).
**Lesson:** If CSRF errors appear on login, check the 401 interceptor first — it might be catching a non-session-expiry 401.

## 2026-05-02 — Deal Pipeline data sync (9 bugs)

### Root problem
Lead data (category, BHK, budget, intent) visible in External Leads but **blank** in Deal Pipeline's qualify form. Multiple causes:

### Fix 1 — "Requirement Sell" / "SALE" label on deal card
**File:** `agents/frontend/src/components/DealPipeline.tsx` ~line 491
**Bug:** Card fell back to `deal.type` (TransactionType enum SALE/RENT) when `demand_property_type` and `demand_type_slug` were null. User saw "SALE · No location" → read as "requirement sell".
**Fix:** Intent-aware label: "Buy · flat · Sector 56" or "Rent · No location". Uses `deal.demand_intent`.

### Fix 2 — Qualify form IIFE missing contact field fallbacks
**File:** DealPipeline.tsx ~lines 901–927
**Bug:** `initialRequirements` IIFE had no fallbacks for `budget_max`, `demand_bhk`, `demand_type_slug`, `demand_main_category`, `demand_category` from the contact.
**Fix:** Added `dc?.budget_max`, `dc?.demand_bhk`, slug resolution via `masterCategories` FK tree as fallbacks.

### Fix 3 — Backend `deal_service.ts` missing contact fields in select
**File:** `agents/backend/src/services/deal_service.ts` `listDeals` (~line 471)
**Fix:** Added missing fields to `demand_contact` select: `budget_max`, `demand_bhk`, `demand_type_slug`, `intent`, `preferred_location`, `category_id`, `sub_category_id`, `type_id`, `demand_main_category`, `demand_category`, `area_min/max/unit`, `timeline`, `demand_amenities`.

### Fix 4 — PATCH /requirements never synced to active deals
**File:** `agents/backend/src/routes/leads.ts` PATCH /requirements
**Bug:** Updating lead requirements only touched Contact; deal snapshot stayed stale.
**Fix:** Fire-and-forget `prisma.transaction.updateMany()` after Contact.update — syncs `demand_budget_min/max`, `demand_bedrooms`, `demand_location`, `demand_amenities`, `demand_intent` to all non-CLOSED deals for that contact.

### Fix 5 — MagicBricks webhook never wrote BHK or classification slugs
**File:** `agents/backend/src/integrations/magicbricks.ts`
**Fix:** Added BHK integer parsing + slug derivation from `lowerPropType`. Now writes `demand_bhk`, `demand_main_category`, `demand_category`, `demand_type_slug`.

### Fix 6 — 99acres poller never wrote classification slugs
**File:** `agents/backend/src/services/ninety_nine_acres_poller.ts`
**Fix:** Added `SLUG_MAP` before upsert. Writes all 3 classification slug fields.

### Fix 7 — Deal interface TypeScript additions
**File:** `agents/frontend/src/api/client.ts`
Added `demand_intent`, `demand_category`, `demand_bedrooms`.

### Fix 8 — 99acres BHK regex wrong
**File:** `ninety_nine_acres_poller.ts` `extractBhk()`
**Bug:** Regex matched "2 BHK" but 99acres sends `"3 Bed"`. BHK always NULL.
**Fix:** `/(\d+)\s*(?:BHK|Bed(?:room)?s?)/i` — matches both.
**Note:** 99acres CmpctLabl doesn't include property-type word; `demand_category` + `demand_type_slug` remain null for most 99acres leads (no type info in feed).

### Fix 9 — MagicBricks sends generic "Residential", specific type is in `msg`
**File:** `magicbricks.ts`
**Bug:** `property_type: "Residential"` hits catch-all branch.
**Fix:** When `property_type === "Residential"`, parse the free-text `msg` field for specific type ("builder floor", "multistorey", "independent house", "villa", "plot", "penthouse", "studio").
