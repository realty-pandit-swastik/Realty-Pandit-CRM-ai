Deal workspace **Match & Share** tab (`frontend/src/components/deal/MatchShareTab.tsx`) has two share buttons:
- **Company WhatsApp** (`sendViaCompanyWA`, MatchShareTab.tsx) → `POST /api/deals/:id/share-properties` → `services/property_sharing.ts:shareSpecificProperty` → `sendPropertyCard()` → Meta **template `rp_property_card_sale_v4`/`rent_v4`** (UTILITY, approved) with `_v2` fallback. IMAGE header + 7 body params + 3 buttons, one card per property. **Full chain verified live end-to-end 2026-05-23 (test send `sent=true` to +917986024171).**
- **Personal WhatsApp** → opens `wa.me/<phone>?text=` with a Detailed text message (built client-side, `sendViaPersonalWA`). Text + listing link only — **wa.me cannot attach images** (link carries photos). Redesigned 2026-05-23 to the "Detailed" layout (title, location, price from `display_price`, area/beds/baths, floor, facing, age, furnishing, amenities, description, link), omitting empty fields + de-duping repeated location tokens. Reads fields added to `MatchedProperty` (matching_engine.ts): city, sub_locality, locality, state, pincode, description, slug, display_id, facing, property_age, display_price (specs+features already present).

**Why clients may not receive Company cards (two real causes):**
1. **MARKETING category wall (dominant).** `rp_property_card_*_v2` are APPROVED but registered **MARKETING** in Meta (code config in `whatsapp_templates.ts` wrongly says `category: 'UTILITY'` — the code label is cosmetic; Meta's own category is what governs delivery). Meta **accepts** the send (returns wamid, we log `Interaction(property_shared)` only AFTER acceptance) but **silently drops delivery** to users who tapped "Stop promotions"/aren't marketing-opted-in. Confirmed via Graph API `message_templates`. No code change can force delivery — fixes require either (a) rebuilding the card as a genuine UTILITY template (changes the promotional copy + needs Meta re-approval; user said keep message same), (b) sending as a free-form session message inside the 24h window (different format, no buttons), or (c) accepting the limitation. **Decision is the user's.** See [project_pending_meta_template_utility] / [feedback_lead_deal_sync_traps].
   - **RESOLVED 2026-05-23 — UTILITY achieved via request-fulfillment framing.** v2/v3 (urgency removed but still "here's a property, book a visit") = Meta classified MARKETING. **v4 reframed as fulfilling the customer's enquiry** — body: *"Namaste 🙏 As requested, here are the details of the property matching your enquiry: … please reply to this message."* — Meta **APPROVED `rp_property_card_sale_v4` + `rent_v4` as UTILITY**. UTILITY bypasses marketing opt-out → cards deliver. **KEY LESSON: a priced property card CAN be UTILITY if framed as a response to the customer's specific request, NOT as a recommendation/offer/promo.** `sendPropertyCard()` (property_sharing.ts) prefers v4, falls back to v2 (v4 4xx fails fast — sendWithRetry skips 4xx — so fallback is one quick call; v4 approved so v2 unused). Same 7 params/image header/buttons as v2 (no send-code change). To create an IMAGE-header template via Graph API: resumable upload needs the CURRENT app id `1868797817103904` ("Panditji"); `.env META_APP_ID` is a DELETED app (see [incident_meta_app_deleted]).
2. **Broken header image (minor, ~1/28).** Some `media_urls[0]` point to files gone from disk (`/uploads/pending/…` 404). Meta downloads the header at send time; a 404 → it rejects the whole card. **Fixed 2026-05-23**: `pickSendableImage()` in property_sharing.ts HEAD-checks (GET fallback, content-type must be `image/`) each media URL and uses the first reachable one, else the brandless `https://realtypandit.in/logo.png`. Applied in both `shareSpecificProperty` + `shareNextProperty`. Verified read-only: of 40 with media, 34 use a real photo, 6 fall back to logo, 4 recovered a valid later photo after a broken first.

**Observability gap:** we do NOT capture outbound wamid and do NOT process Meta delivery-`statuses` webhooks (the `WhatsAppMessage` model exists with a `status` field but is unused for outbound). So "did the card deliver?" can't be answered from our DB — only "Meta accepted it." Building this is an open option.

**Inventory data reality (audit 2026-05-23, 350 active):** missing BHK/bedrooms **95%**, amenities 79%, description 93%, **no image 53%**; area/locality/display_price ~100% present. So shared cards/messages look sparse because the listings are thin, not because of formatting.

**BHK fix (2026-05-23):** since 95% lack `specs.bhk_count` but the `slug` encodes it (`3bhk-villa-…`), both paths now use `bhkFromSlug()` as a fallback (`specs.bhk_count || specs.bedrooms || bhkFromSlug(slug)`) — in `sendViaPersonalWA` (frontend) and `shareSpecificProperty`/`shareNextProperty` (backend Company-card bhk param, no template change). A real `specs.bhk_count` backfill from slug remains a worthwhile data task.

Infra notes: backend serves `/uploads` via `express.static(process.cwd()+'/uploads')` (cwd `/var/www/realty-pandit/backend`), proxied on both `api.` and `admin.` (port 7071). `display_price` is the website/public price; the raw `price` column is inconsistent (sometimes 10× off) — always prefer `display_price` for customer-facing output.
