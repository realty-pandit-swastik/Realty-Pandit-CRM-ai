## Original confirmed findings — historical triggers and correction scope

### P1 — Appointment serialization bypasses inventory owner-field redaction

**Existing backend defect exposed by the integrated native appointment flow; fix assigned separately.** An employee assigned a visit can access its linked property even when another employee owns the property and it is not shared. Calendar routes used `property: true`, serializing `owner_phone`, `owner_id`, `key_holder_phone`, `flat_no` and `plot_no`. The canonical inventory staff serializer hides those fields from that employee. Client parsing that ignores the fields does not protect the API response.

Paths: `agents/backend/src/routes/calendar.ts`; canonical `redactInventoryForStaff` in `agents/backend/src/routes/inventory.ts`; native appointment readers in `agents/mobile/app/visits/[id].tsx` and visit lists/Home.

Smallest shared fix: apply the existing inventory redaction policy to nested appointment properties across every calendar response that returns them, preserving the already authorized appointment and public property context. Customer-facing price is intentionally visible to staff; there is no separate price or Tenant-secret finding here.

Meaningful check: real-auth/disposable-DB employee E assigned a visit to employee F's unshared property; list/detail/update responses retain the visit and safe context while excluding all canonical restricted owner/location fields. Check authorized owner/manager behavior and existing web response compatibility. The parent assigned the fix and regression to `calendar_privacy_fix`; that agent's later evidence must establish closure.

### P1 — Task detail reveals a project that its own endpoint denies

**Existing backend defect retained during scope integration; fix assigned separately.** A manager can create a project, omit employee E from its membership, and assign E a task linked to that project. The manager legitimately passes `validateTaskReferences`. E's task passes `scope.tasks`: the assignee is E and the project owner belongs to the tenant. E's `GET /api/projects/:id` correctly returns 404 because `scope.projects` requires owner/team access, but `GET /api/tasks/:id` uses `include: { project: true }` and returns the project's entire description, owner/member IDs, dates and status.

Paths: `agents/backend/src/services/task_scope.ts` (`resolveTaskScope`, `validateTaskReferences`); `agents/backend/src/routes/tasks.ts` single-task read; `WorkProject` in `agents/backend/prisma/schema.prisma`. Native `app/task/[id].tsx` needs only project ID/name context. Existing task list/create/update already select only those two nested fields; the web TaskBoard consumes the same context.

Smallest shared fix: make task-detail nested project selection match the existing `{ id, name }` selection. Do not broaden project membership or hide otherwise valid assigned tasks to resolve this response inconsistency.

Meaningful check: real-auth/disposable-DB manager-owned project with E assigned a linked task and absent from `team_members`; assert project detail denial, task detail success and exact safe nested keys. Retain tenant/peer negatives and the existing task/web contracts. The parent assigned the fix and regression to `calendar_privacy_fix`; closure requires its later evidence.

### P2 — Interrupted attachment uploads enable another create before reconciliation

**Preexisting integrated native safety gap, still open at this review checkpoint.** After the server saves a photo/document but its response is lost, `ApiClient` correctly raises an ambiguous write. `Attachments.perform` stores only the error text, leaves `pending` selected, then enables **Retry selected attachment** immediately. Its notice asks the user to refresh/check, but no explicit refresh or successful reconciliation gates that second POST. `send`'s permission GET checks `canEdit`; it does not check whether the previous upload already succeeded. A retry can therefore append a second photo or create another private document/file.

Paths: `agents/mobile/src/features/inventory/Attachments.tsx` (`perform`, `send`, pending retry controls); `src/features/inventory/attachmentFiles.ts` (`uploadAttachment`); `src/api/client.ts` (write ambiguity); backend `routes/inventory.ts` `POST /:id/upload` appends media, and `POST /:id/documents` creates a new UUID file/document without an idempotency key. This is manual retry risk, not an automatic mutation queue.

Smallest complete fix: retain the `ApiError.ambiguous` outcome in attachment state, block retry until an explicit successful property/attachment refresh and user review, and keep the selected file/input available. Failed/offline refresh must not unlock retry. Preserve ordinary retry after a definite rejection and cancellation/discard behavior. No new dependency or server idempotency mechanism is needed for this narrow correction.

Meaningful check: component test simulates an upload accepted server-side followed by a timeout/5xx or unreadable success; assert a second POST cannot occur before explicit successful refresh/review, the file stays available, and failed refresh keeps the gate. Then show permitted retry after reconciliation and ordinary retry for definite 4xx. The parent has accepted this for a separate narrow fix; this report does not claim closure.
